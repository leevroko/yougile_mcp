# Release Policy: yougile-mcp

Политика версионирования, коммитов, changelog и релизов. Построена на:

- **SemVer 2.0** — версия `MAJOR.MINOR.PATCH`, проект сейчас в `0.x` (нестабильный публичный API);
- **Conventional Commits 1.0** — формат коммит-сообщений, из которого механически выводится bump версии;
- **Keep a Changelog** — ручной `CHANGELOG.md` в корне репозитория;
- **Ручные теги** — версию объявляет человек (`git tag -a vX.Y.Z`), CI собирает и публикует релиз по тегу.

---

## 1. Публичный API (что защищает SemVer)

Для MCP-сервера «публичный API» — это не только Go-пакеты:

| Слой | Стабильный контракт |
|------|---------------------|
| MCP-инструменты | набор имён инструментов, их параметры (обязательность, типы), формат ответов (json/markdown) |
| CLI | подкоманды (`serve`, `init`), флаги (`--addr`, `--config`), их значения по умолчанию |
| Конфиг `~/.config/yougile-mcp/config.json` | схема полей (`mode`, `permissions`, `agent_id`, `mcp_url`, `pi_scope`, …) |
| Env-переменные | `YOUGILE_CONFIG`, `YOUGILE_AGENT_ID`, `YOUGILE_MCP_URL`, `YOUGILE_BASE_URL`, `YOUGILE_MEMORY_DIR`, `YOUGILE_PI_EXT` |
| pi-extension | команды (`/yougile-status`, `/yougile-mode`, `/yougile-on`), поведение fallback, формат сообщений |
| Формат `audit.jsonl` | поля записей (на него могут завязаться внешние дашборды) |

Внутренние Go-пакеты (`internal/*`) стабильностью **не** обладают — это детали реализации.

## 2. Версионирование (фаза 0.x)

Проект в `0.x`: контракт разрешено менять в минорных версиях.

| Изменение | Bump (0.x) | Bump (после 1.0) |
|-----------|------------|------------------|
| Новый MCP-инструмент, подкоманда, опциональный параметр | `MINOR` | `MINOR` |
| Исправление бага без изменения контракта | `PATCH` | `PATCH` |
| Производительность, внутренний рефакторинг | `PATCH` | `PATCH` |
| **Breaking change** (см. §3) | `MINOR` | `MAJOR` |
| Только `docs:` / `chore:` / `ci:` | без релиза | без релиза |

Переход на `1.0.0` — отдельное решение (критерий: контракт MCP-инструментов заморожен и используется внешними потребителями, например OpenClaw-сервером в проде).

## 3. Что считается breaking change

Конкретный список для этого репозитория:

- удаление или переименование MCP-инструмента / параметра инструмента;
- новый **обязательный** параметр инструмента;
- изменение формата ответа инструмента (поля json, структура markdown) — кроме добавления новых полей;
- удаление/переименование env-переменной, CLI-флага, подкоманды;
- несовместимое изменение схемы `config.json` (старый конфиг не читается);
- изменение значений по умолчанию с другим поведением (например, дефолтный `mode`);
- смена формата `audit.jsonl` в несовместимую сторону.

Каждый breaking change коммит помечается футером `BREAKING CHANGE: <описание>` (или `!` после типа: `feat(mcp)!:`).

## 4. Conventional Commits

Формат:

```
<type>(<scope>)!: <краткое описание, русский или английский, императив>

<опциональное тело: что и почему>

<опциональные футеры>
BREAKING CHANGE: <что сломано и как мигрировать>
Fixes #N            — закрывает issue N (GitHub закроет при попадании в master)
Refs #N             — просто ссылка
```

**Типы**: `feat` (новая возможность → MINOR), `fix` (багфикс → PATCH), `perf`, `refactor`, `docs`, `test`, `ci`, `chore`. Релизный коммит changelog'а — `docs(changelog): ...`.

**Scopes** (словарь проекта): `mcp`, `board`, `task`, `sticker`, `chat`, `http`, `config`, `audit`, `pi-ext`, `deploy`, `cli`.

Примеры из истории:

```
feat(mcp): task chat — get_task_messages + send_task_message …
fix(pi-ext): preserve foreign tools in setActiveTools + project cwd-guard (fixes #1)
perf(board): concurrent snapshot with bounded parallelism + deadline + burst (fixes #2)
feat(mcp)!: rename columnId to boardColumnId in list_tasks   # гипотетический breaking
```

Правила:
- один коммит = одно логическое изменение (не смешивать `feat` и `fix`);
- описание в настоящем времени, до ~72 символов, без точки в конце;
- issue закрывается только через `Fixes #N` в коммите, попавшем в master.

## 5. Changelog (`CHANGELOG.md`, Keep a Changelog)

- Секция `## [Unreleased]` всегда присутствует сверху — новые записи падают туда в момент коммита (кто сделал изменение, тот и записал);
- порядок подсекций: `Added`, `Changed`, `Fixed`, `Security`, `Performance`, `Removed`, `Deprecated`;
- запись — одна строка, пользовательский эффект, без хешей коммитов и без внутренней кухонной детали («инструмент create_sticker» ✓, «рефактор SessionRegistry» — только если видимо пользователю);
- при релизе секция `Unreleased` переименовывается в `[X.Y.Z] — YYYY-MM-DD` и создаётся новая пустая `Unreleased`;
- прошлое (до введения политики) зафиксировано в changelog ретроспективно и **тегами не помечается** — первый настоящий тег объявляет текущую версию.

## 6. Релизный процесс (ручной тег + CI)

Master всегда зелёный: каждый push/PR гоняет CI (`go vet`, `go test ./...`, сборка).

Выпуск версии:

```bash
# 1. CHANGELOG.md: Unreleased → [X.Y.Z] — дата, новая пустая Unreleased
# 2. Коммит: docs(changelog): release v0.5.0
git add CHANGELOG.md && git commit -m "docs(changelog): release vX.Y.Z"

# 3. Аннотированный тег на этом коммите (не lightweight!)
git tag -a vX.Y.Z -m "yougile-mcp vX.Y.Z"

# 4. Push ветки и тега
git push && git push origin vX.Y.Z
```

Дальше CI (`.github/workflows/release.yml`) автоматически:

1. прогоняет тесты;
2. собирает статические бинари `yougile-mcp-linux-amd64` и `yougile-mcp-linux-arm64` (CGO выключен);
3. считает `sha256sum`;
4. создаёт GitHub Release `vX.Y.Z` с секцией этой версии из `CHANGELOG.md` в качестве notes и бинарями как артефактами.

Откат релиза — невозможно полностью (тег уже в upstream): по договорённости bad-release закрывается `vX.Y.Z+1` (в SemVer это идентификатор сборки, для простоты используем следующий PATCH).

### Хотфикс

Репозиторий single-maintainer, веток нет: фикс идёт сразу в master (`fix: ...` + запись в `Unreleased`), затем обычный релизный процесс с PATCH-тегом.

## 7. Ответственность CI

| Workflow | Триггер | Что делает |
|----------|---------|------------|
| `ci.yml` | push в master, PR | `go vet`, `go test ./...`, `go build` — защита от поломки master |
| `release.yml` | push тега `v*` | тесты → сборка amd64/arm64 → sha256 → GitHub Release с notes из changelog |

CI **не** решает, какая это версия и когда релизить — это всегда ручное решение (тег). CI только собирает и публикует.

## 8. Как начать с текущего состояния

- На момент ввода политики состояние кода описано в changelog как **v0.5.0 (ретроспектива, тег не выставлялся)**;
- первый реальный тег — на текущем или ближайшем коммите: `git tag -a v0.5.0` (если хотим зафиксировать актуальное состояние) либо сразу следующий `v0.6.0` при следующем `feat`;
- все последующие версии — строго по этой политике.
