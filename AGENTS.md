## Architecture

### DDD Layering (реализовано)

```
┌─────────────────────────────────────────────────────┐
│                    MCP Layer                         │
│  (internal/mcp/) — MCP-сервер, инструменты, хендлеры │
│  Адаптирует сервисы для вызовов ИИ-ассистента        │
└───────────────────────┬─────────────────────────────┘
                        │ вызовы сервисов
┌───────────────────────▼─────────────────────────────┐
│                  Service Layer                       │
│  (internal/service/) — бизнес-логика, агрегация       │
│  BoardService, TaskService, ReviewService,           │
│  AuditService, GoalService, CompressionService       │
│  Прямые вызовы между сервисами (без Event Bus)       │
└──────┬───────────────────────────────────────────────┘
       │ имплементация
┌──────▼─────────────────────────────────────────────┐
│              Infrastructure Layer                    │
│  (internal/infrastructure/)                          │
│  ─ http/: RoundTripper (auth → rate limiter → retry) │
│  ─ repository/: HTTP-реализации репозиториев         │
└──────────────────────┬──────────────────────────────┘
                       │ HTTP-запросы
              ┌────────▼────────┐
              │ YouGile API v2  │
              │ /api-v2/*       │
              └─────────────────┘
```

### Ключевые архитектурные решения

1. **DDD (Domain-Driven Design)** — каждый доменный пакет самодостаточен: entity, value objects, repository interface. Никаких общего `models.go`.
2. **HTTP-клиент через RoundTripper** — middleware-цепочка: Bearer auth → Token bucket rate limiter → Retry → HTTP-транспорт. Никаких обёрток поверх `http.Client`.
3. **Прямые вызовы между сервисами** (вместо Event Bus) — сервисы вызывают друг друга напрямую, без pub/sub. Связи однонаправленные, без циклов (см. SERVICES.md §9).
4. **Ручная пагинация** — API не поддерживает cursor-based пагинацию. Только `offset += limit` пока `paging.next === true`.
5. **Минимум зависимостей** — только MCP SDK (`github.com/mark3labs/mcp-go`), всё остальное стандартная библиотека Go.

### Error Handling

- Ошибки как значения (Go-идиома): `if err != nil { return fmt.Errorf("context: %w", err) }`
- Доменные ошибки: `var ErrTaskNotFound = errors.New("task not found")`
- HTTP-статусы маппятся в доменные ошибки: `404 → ErrNotFound`, `429 → ErrRateLimited`
- Нет паник (кроме как в `main()` при фатальной инициализации)
- Нет сторонних библиотек для ошибок (только `fmt.Errorf` + `errors.New`)

### Testing

- Фреймворк: стандартный `go test`
- Паттерн: table-driven тесты (предпочтительно)
- Расположение: `<package>_test.go` рядом с тестируемым файлом
- Моки: ручные (интерфейсы + реализации-заглушки), никаких mock-генераторов
- HTTP-тесты: `httptest.NewServer` для тестирования RoundTripper и репозиториев

### Git Commits

- Формат: `type: short description` (conventional commits, но без строгости semver)
- Примеры: `feat: add HTTP client with rate limiter`, `fix: handle 429 retry-after header`, `docs: add API reference for user endpoints`

## Architecture Patterns (реализовано)

### Repository Pattern

```go
// internal/domain/task/repository.go — интерфейс в domain
type Repository interface {
    List(ctx context.Context, filter TaskFilter) ([]Task, PagingMetadata, error)
    GetByID(ctx context.Context, id TaskID) (Task, error)
    Create(ctx context.Context, req CreateTaskRequest) (TaskID, error)
    Update(ctx context.Context, id TaskID, req UpdateTaskRequest) error
}

// internal/infrastructure/repository/task_repository.go — реализация в infrastructure
type taskRepository struct {
    client *http.Client
    baseURL string
}
```

### RoundTripper Middleware Chain

```go
// internal/infrastructure/http/round_tripper.go
// Композиция: BearerAuth → RateLimiter → Retry → base transport
type bearerAuthTransport struct { rt http.RoundTripper; token string }
type rateLimitTransport struct { rt http.RoundTripper; bucket *rate.Limiter }
type retryTransport struct { rt http.RoundTripper; maxRetries int }
```

### Value Object Pattern

```go
// internal/domain/valueobject/id.go
type TaskID struct { value string }  // UUID validation in constructor
func NewTaskID(s string) (TaskID, error) { ... }
func (id TaskID) String() string { return id.value }
```

### Service Call Pattern (вместо Event Bus)

```go
// internal/service/review/review.go
// Прямой вызов другого сервиса (владельца данных) вместо событий
func (s *reviewService) Summarize(ctx context.Context, boardID valueobject.BoardID, since *int64) (Summary, error) {
    snap, err := s.boards.GetBoardSnapshot(ctx, boardID, since)
    // ... агрегация метрик
}
```

**Принцип**: связи направлены от «потребителя» к «провайдеру» (сервис, владеющий данными). Если связь станет двунаправленной — вынести общий код в низкоуровневый сервис.

## Known API Uncertainties

Из `API_REFERENCE.md` (раздел 19), требуют экспериментальной проверки на реальном API:

1. **`/companies{*companyId}`** — URL без слеша между `companies` и ID (баг spec'а?)
2. **`stickers.custom` в `StickersDto` доски** — формат поля не специфицирован
3. **Взаимосвязь `/stickers` и `/string-stickers`** — старый и новый механизмы стикеров
4. **Формат ошибок** — тело ответа при 400/401/404/429
5. **Наличие `paging`** в BoardListDto, ColumnListDto (не указано в spec)
6. **`GET /tasks?boardId=` без `columnId`** — возвращает ли все задачи доски одним запросом? Если да — срезает 8 запросов по колонкам до 1
