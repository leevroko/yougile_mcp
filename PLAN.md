## 1. API Reference

Полный справочник эндпоинтов, DTO и форматов данных: [`API_REFERENCE.md`](API_REFERENCE.md)

**Источник**: https://ru.yougile.com/api-json (официальный OpenAPI spec, загружен 2026-05-19)
**Base URL**: `https://ru.yougile.com/api-v2`
**Auth**: `Authorization: Bearer {apiKey}`
**Rate Limit**: 50 req/min

Группы эндпоинтов:
- Auth (4 эндпоинта) — получение/управление API-ключами
- Users (6 эндпоинтов) — CRUD сотрудников
- Company (2 эндпоинта) — детали и изменение компании
- Projects (4 эндпоинта) — CRUD проектов
- Project Roles (5 эндпоинтов) — управление ролями и правами
- Departments (4 эндпоинта) — CRUD отделов
- Boards (4 эндпоинта) — CRUD досок
- Columns (4 эндпоинта) — CRUD колонок
- Tasks (7 эндпоинтов) — CRUD задач, чат-подписчики, два list-эндпоинта (прямой/обратный порядок)
- Stickers (старые, 3 эндпоинта) — кастомные поля (string/select/number/date/user)
- String Stickers (новые, 7 эндпоинтов) — dropdown-стикеры с состояниями
- Sprint Stickers (новые, 7 эндпоинтов) — спринт-стикеры с датами

Пагинация: ручное управление `offset += limit` пока `paging.next === true`.
Формат: `PagingMetadata { count, limit, offset, next }`.

Известные неопределённости (требуют экспериментальной проверки):
- `/companies{*companyId}` — URL без слеша между `companies` и ID
- `stickers.custom` в `StickersDto` доски — формат не специфицирован
- Взаимосвязь `/stickers` и `/string-stickers`
- Формат тела ошибок (400/401/404/429)
- Наличие `paging` в BoardListDto, ColumnListDto

Сценарии определяются **до** дизайна модели: DDD-сущности и агрегаты выстраиваются под типичные бизнес-задачи ИИ-ассистента, а не наоборот.

Типичные сценарии работы:

- **Bulk move** — перемещение группы задач между колонками (например, все просроченные → Review)
- **Summarize** — сводка по доске (группировка, метрики, рекомендации) — замена daily_review.py
- **Audit** — поиск просрочки, задач без стикеров, автоматическое перемещение
- **Goal tracking** — отслеживание прогресса целей (weighted KR по стикерам Weight и Progress)
- **Quick actions** — быстрое создание/перемещение/обновление задач
- **Batch stickers** — массовое обновление стикеров у группы задач
- **Compression** — цепочка daily → weekly → monthly → yearly review

Для каждого сценария определить:
- Входные/выходные данные
- Какие API-эндпоинты нужны
- Какие сущности участвуют (уточняются на шаге 3)
- Граничные случаи

### Стоимость сценариев в API-запросах

Оценка по легаси-скриптам и OpenAPI spec:

| Сценарий | Запросы (сейчас) | Избыточность |
|----------|------------------|--------------|
| List tasks | 9 (колонки + 8× задачи по колонкам) | структура доски грузится каждый раз |
| Summarize | 9–17 (8 колонок + стикеры + пагинация) | то же + повторная расшифровка стикеров |
| Audit | 9 + N×PUT | то же + N мутаций |
| Goal tracking | 9–10 | то же + повторная расшифровка стикеров |
| Quick actions | 1 | минимальна |
| Batch stickers | N×PUT | нет batch-эндпоинта |
| Compression | 9–17 | то же, что Summarize |

Источники избыточности:
- Каждый сценарий заново грузит структуру доски (колонки, стикеры, проекты) — меняется редко, но дёргается всегда
- N запросов по колонкам вместо одного (см. API_REFERENCE.md раздел 19, п. 6 — кандидат на проверку `GET /tasks?boardId=` без columnId)
- Расшифровка стикеров: задача хранит `{stickerUUID: value}`, нужна карта доски `GET /stickers?boardId=` (1 кэшируемый запрос)
- Нет batch-эндпоинтов: bulk move / batch stickers = N×PUT неизбежно

### Принципы оптимизации (согласовано)

> Основная единица стоимости — не API-запрос, а **вызов MCP-инструмента** (1 вызов = 1 раунд LLM + вброс результата в контекст). Оптимизация направлена на сокращение вызовов инструментов, а не только запросов.

1. **Гибрид двух слоёв инструментов**
   - Слой 1 — тонкий CRUD: `list_projects`, `list_boards`, `list_columns`, `list_tasks`, `get_task`, `create_task`, `update_task`, `get_stickers` — точечные операции и отладка
   - Слой 2 — композитные (1 вызов покрывает весь сценарий): `get_board_snapshot`, `summarize_board`, `audit_board`, `track_goals`, `bulk_move_tasks`, `batch_update_stickers`, `compress_reviews`
2. **Вложенные справочные данные**: list-инструменты возвращают названия колонок + легенду стикеров прямо в ответе (агент не дёргает `list_columns`/`get_stickers` отдельно)
3. **Формат вывода**: параметр `format: json|markdown`. Аналитика → markdown по умолчанию (TL;DR сверху 3–5 строк, детали ниже), CRUD → JSON. Сервис всегда возвращает структурированные данные; markdown — отдельный презентационный слой с шаблонами
4. **Пагинация — всегда полные данные**: композитные проходят все страницы (`offset += limit` пока `next === true`). Чинит баг легаси (терял данные при >100 задач). Приоритет — точность, токены вторичны
5. **Дельта-обновления**: параметр `since` (timestamp) — возврат только изменённых задач; для периодического опроса агента
6. **Без TTL-кэша на старте** — добавить позже по реальной нагрузке

## 5. Дизайн кодовых решений

Архитектурные и технические решения для реализации спроектированной системы:

- **Go Package Structure** — инициализация Go-модуля, структура директорий в соответствии с DDD
- **HTTP-клиент** — кастомный RoundTripper: Bearer auth → Token bucket rate limiter (50 req/min) → Retry с exponential backoff → HTTP transport
- **Слой репозиториев** — интерфейсы в domain, HTTP-реализации в infrastructure. Обработка пагинации, маппинг HTTP-статусов в доменные ошибки.
- **Экспериментальная верификация API** — реальные запросы к YouGile API для проверки неопределённостей из шага 1
- **MCP-интеграция** — сопоставление сервисов с MCP-инструментами (12 инструментов: list_projects, list_boards, list_columns, list_tasks, create_task, update_task, bulk_move_tasks, batch_update_stickers, summarize_board, audit_board, track_goals, compress_reviews)
- **Обработка ошибок** — иерархия доменных ошибок, маппинг HTTP-статусов
- **Конфигурация** — API-ключ и companyId через переменные окружения

**Результат**: Документированные решения (ADRs) и скорректированная структура пакетов.
